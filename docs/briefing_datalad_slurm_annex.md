# BIDS Apps Runner: DataLad + SLURM provenance pipeline, and why we replaced datalad-slurm

**Repo:** https://github.com/MRI-Lab-Graz/bids_apps_runner
**On the cluster:** `/usr/people/mrilabgraz/github/bids_apps_runner`
**Own tooling:** `annex-slurm/bin/` (`annex-slurm-schedule`, `annex-slurm-finish`), design spec `docs/superpowers/specs/2026-09-09-annex-slurm-design.md`

Scope: the DataLad / SLURM / container / push-back mechanics. The OpenNeuro mega-study (MRIQC, fMRIPrep, connectoflow) is a side project and is not covered here.

---

## 1. Architecture in one picture

```
 datalad-server (SSH alias, origin)                     shared HPC storage (/cl_tmp/mrilabgraz)
 ┌──────────────────────────┐   clone (metadata only)   ┌───────────────────────────────┐
 │ input BIDS dataset       │ ────────────────────────► │ input clone                   │
 │ output dataset           │ ◄──── push (git + annex)  │ output clone (derivatives     │
 │   branch: derivatives    │                           │   branch, nested DataLad ds)  │
 └──────────────────────────┘                           └──────────────┬────────────────┘
                                                                       │ bind mounts
                    login node: submit only                            ▼
   submit_bids_cohort.sh ──► sbatch array ──► compute node: apptainer exec --cleanenv
        │                     (1 task/subject)   -B input:/bids:ro  -B output:/output  -B tmp:/tmp
        └──► dependent finish job (--dependency=afterany) ──► commit + push
```

**Invariant: the array tasks contain no datalad or git calls.** `scripts/hpc_datalad_runner.py` generates plain SLURM scripts that only do compute. All git/annex state changes happen in a single sequential place, the finish job. This replaces per-job git operations serialized with `flock`, which is the usual failure mode with naive "datalad run in every array task".

## 2. Lifecycle (`scripts/submit_bids_cohort.sh`)

1. **setup (once, idempotent):**
   - Pre-clone the input datasets to shared storage (metadata only).
   - Create the output DataLad dataset on the server and register it as `derivatives/<app>` on a `derivatives` branch.
   - Before this, a pre-flight check (`check_derivatives_conflicts.py`) detects plain-tracked `derivatives/<app>` content that would make `datalad create` or `git submodule add` fail.
2. **submit:**
   - Build the subject list from the pre-clone.
   - **Prefetch once, sequentially**, only this cohort's subjects and only the datatypes the app needs (`app_profiles.py` `required_datatypes`). This is never done in array tasks. It is dispatched to a compute node when launched from a login node (`lib_prefetch.sh`).
   - Check the output clone against `origin/derivatives`: fast-forward if behind, refuse if diverged.
   - Generate the array script, then schedule it with `annex_schedule_batch` (`lib_annex_paths.sh`): `annex-slurm-schedule` unlocks only the *existing* output of this batch's subjects (plus loose dataset-root files) — explicit paths, never the whole tree — and submits with `sbatch --parsable`.
3. **Batching:** the cohort is split into sequential batches (`hpc.batch_size`, default 10). Each batch has its own array job and finish job, so a slow or failed finish costs one batch, not the whole study. The next batch is submitted from the previous batch's finish job (`_continue-*-batch`). It is not pre-scheduled with `--dependency`: annex-slurm supports strictly sequential batches only, because a batch's unlock must not race the previous batch's commit.
4. **finish job** (`--dependency=afterany`, 4 CPUs, 8 GB, 12 h) runs `scripts/annex_cohort_finish.sh` (2026-10, replacing `incremental_datalad_save.sh` + `slurm-finish` + `datalad push`, all of which compare index against worktree and hang on drifted repos):
   - Per subject / timepoint it lists the not-yet-annexed files with `find` (a filesystem listing, no git) and commits them through `annex-slurm-finish` in chunks. Because the job is `afterany`, a TIMEOUT'd task's partial output is committed too, not abandoned as untracked. An interruption costs one chunk; re-running resumes (committed files are symlinks and are skipped).
   - `--root-files` / `--extra PATH` add the loose dataset-root reports, the array's own SLURM logs (`.slurm_logs/<ds>`) and `subregion_results/`.
   - `annex-slurm-finish` pushes the branch and the `git-annex` branch and checksum-verifies every object on the remote (see §5).
5. **The completion contract** (a re-scan, not an exit code): `annex_cohort_finish.sh` exits 0 only if a final `find` still finds **no regular (unannexed) file** under any listed subject — the check that would have caught the 132 empty commits. Failure triggers an ntfy push notification. The end-to-end test under a real scheduler is `annex-slurm/test/cohort_flow_e2e.sh`.

## 3. Container integration

Generated by `hpc_datalad_runner.py` per app profile:

- `apptainer` is preferred, with a `singularity` fallback. The binary that ran is logged.
- `--cleanenv` is always set. For GPU jobs the CUDA env needs explicit passthrough (`--nv` is added when GPUs are requested).
- Binds: `-B $BIDS_DIR:/bids:ro`, `-B $OUT_DIR:/output`, `-B $TMP_DIR:/tmp`, plus app-specific extras (e.g. the FreeSurfer license).
- Input is read-only, output is a writable output-clone path, and scratch is per-task.
- Per-app execution adapters: FastSurfer BIDS, FreeSurfer-BIDS (cross-sectional → base → longitudinal in one call), and the generic BIDS-app `run` path. Resource flags (`--nprocs`, `--mem`) are derived from the SLURM request.
- Because the container only ever sees plain directories, nothing in it needs git or annex.

## 4. Why datalad-slurm broke on large datasets

`datalad slurm-schedule -o .` first unlocks the whole output dataset, then submits. `slurm-finish` and `datalad save` then do a full index / working-tree / object-graph comparison.

On dataset 134 (FreeSurfer longitudinal, ~142K annexed objects, ~249K tracked paths) the git-annex **keys DB accumulated reconciliation drift**. Weeks of interrupted write operations caused it: dropped sessions, walltime TIMEOUTs, killed debugging attempts. After that, every command that has to *compare* state hangs. This is verified in isolation, regardless of scope:

| Hangs (any scope) | Fast (reads/writes already-known state) |
|---|---|
| `git status`, `diff`, `add`, `fsck`, `read-tree HEAD` | `git ls-tree`, `write-tree`, `commit-tree`, `update-ref` |
| `datalad unlock / status / save / slurm-*` | `git annex calckey`, `setkey`, `fromkey`, `contentlocation`, `setpresentkey` |
| `git annex copy --to` (its P2P path re-reads local content) | `rsync` of raw objects, ref-level `git push` |
| `git annex lock` (43 min at 0% CPU, unreaped zombies) | `git annex unlock` (materializes from a known key, no compare) |

Side effect: a login-node `submit` killed mid-`slurm-schedule -o .` once left 142,592 files unlocked with no finish job to re-lock them.

## 5. annex-slurm: the replacement

**Idea:** the caller already knows the array job's declared outputs, so nothing needs to be discovered by comparison. Two commands, explicit paths only (never `-o .`), no datalad dependency, no bookkeeping DB. SLURM's `squeue`/`sacct` is the only job state. That is sufficient because batches are strictly sequential.

**`annex-slurm-schedule -o PATH… -- <sbatch args>`**
- `git annex unlock -- PATH` per existing tracked path. This takes 0.18 s for a file and ~6 s for a ~2000-file subject directory.
- Then `exec sbatch`.

**`annex-slurm-finish -m MSG PATH…`**
1. `calckey`, then capture the size **before** `timeout --kill-after=10 30 git annex setkey` (setkey *moves* the content). If setkey is killed mid-finalize, the object has still landed, so `fromkey` recreates the symlink. Verify with `contentlocation` and a size check.
2. Build the commit in a **temporary `GIT_INDEX_FILE`**:
   - Seed it from `read-tree <HEAD-tree-sha>`, with an explicit tree-ish. This is object-graph only, unlike `read-tree HEAD`.
   - Stage each path with `update-index --cacheinfo 120000,<blob>,<path>`.
   - `write-tree`, then `commit-tree -p HEAD`, then `update-ref`.
   - The real index is never touched. It carries unrelated drift (33,737 of 248,827 paths differed from HEAD).
3. **Gate:** `ls-tree -r <tree> -- paths` must exactly equal the staged entries, otherwise refuse to commit.
4. `git push origin <branch>`, verified via `ls-remote`. The real index is then synced from the tree object via `ls-tree | update-index --index-info`.
5. **Content goes via `rsync -aR --files-from`**, not `git annex copy`:
   - Object paths come from `readlink -f` + `realpath --relative-to` (annex hash dirs are identical on both ends).
   - Remote sizes are verified over ssh `stat`.
   - Presence is recorded with one batched `git annex setpresentkey --batch` (`KEY UUID 1` lines), and verified with `whereis --key`.

**Bugs found in real runs (all now baked in or tested):**
- Working files on compute-node-invisible paths. Jobs failed instantly, so everything must be on shared storage.
- `setkey` consumes its input, so verifying size in a later pass failed every file. It cost a ~2.5 h recompute.
- `stat` on an already-annexed symlink reports the link length, so `-L` is needed.
- **`git annex fromkey` silently no-ops when the symlink already matches the key.** This produced **132 consecutive empty commits over 4 days** while every check passed. The fix was `update-index --cacheinfo` plus the tree gate above. Regression test: `annex-slurm/test/smoke_test.sh`.

**Validation:** dataset 134's full run: 117 subjects, 306 longitudinal timepoints, 7,903 subregion files. The `derivatives` branch on the server was independently confirmed to match the local commit, and the content was confirmed present via `whereis` from a fresh session.

### Why rsync instead of `git annex copy`

This is a deliberate workaround for the keys-DB drift on 134, not a preference. It is a trade-off, so here are both sides.

**Why `git annex copy --to origin` was ruled out:** it hung even when scoped to a single already-known `--key`. To stream content over its P2P protocol, git-annex has to read the local object, and that goes through the same keys-DB reconciliation that hangs every other compare-type command. `git annex move`, `drop` and `get` were not needed, so they were not tested.

**What replaces it:**
1. `rsync -aR --files-from` copies the objects under `.git/annex/objects/<hash>/<hash>/<key>/<key>` to the identical relative path in the remote repo. This relies on the hash-directory layout being deterministic and identical on both ends.
2. Each remote object's size is compared with the local one (ssh `stat`).
3. `git annex setpresentkey --batch` records "this key is present in remote UUID" in the local `git-annex` branch.

**What we gave up, and how it is covered (changed 2026-10-02, tests in `annex-slurm/test/smoke_test.sh`):**
- **Integrity:** after rsync, each remote object is hashed over ssh (`sha256sum` or `md5sum`) and compared with the key, which is the content hash for SHA256E/SHA256 and MD5E/MD5. This is the check `git annex copy` would have done. Same-size corruption, and rsync skipping a stale same-size/same-mtime object, are now rejected (`CHECKSUM MISMATCH`). MD5E matters: `datalad create` datasets (e.g. our fmriprep outputs) use `annex.backend=MD5E`, and the first version of this check only handled SHA256, so it would have fallen back to size-only on exactly those datasets. Other backends fall back to size-only with a warning. The cost is one remote read of every pushed object.
- **`setpresentkey` is still an assertion**, but it now runs only after the size and hash checks above pass.
- **Remote visibility:** after `setpresentkey`, `annex-slurm-finish` pushes the `git-annex` branch, so the server's location log matches its objects. A non-fast-forward fails loudly, with no force.
- **Layout assumption:** still real. It holds for our repos (same git-annex version, same hash-dir style on both ends). It would break against a special remote or a different hash style.
- **Ordering caveat (not changed):** the branch is pushed before the content is copied and verified. A failed verification therefore leaves a pushed commit whose content is not yet on the server. Re-running finish repairs it.

**Position to take with him:** the intended end state is plain `git annex copy`/`datalad push`. rsync is the bypass for one specific broken state. On a repo without drift the stock commands are the right choice. If we fix or rebuild 134's keys DB, this step goes away.

### What "no concurrent or overlapping batches" means

datalad-slurm keeps an **open-jobs DB**: `slurm-schedule` registers the job and its declared outputs, `slurm-finish` closes it. It refuses to schedule a job whose outputs overlap an open one. Because our batches share the same output dataset (`-o .`), every batch overlaps every other.

So our cohorts run **batch N+1 only after batch N's finish job has committed and pushed**. The finish job submits the next batch itself. This is deliberately sequential, and cohort-level parallelism comes from the array within each batch and from running different datasets side by side.

For annex-slurm the same limit holds for a different reason. It has no bookkeeping DB, so two overlapping batches would not be refused. Two finish jobs would simply both do `commit-tree -p HEAD` + `update-ref` on the same branch. The second would build its commit from a stale HEAD, and one commit would silently drop the other's paths, or the push would be rejected as non-fast-forward. We don't guard against that. We rely on strict sequencing, and SLURM's own state is the only record of what is running.

**Guard (added 2026-10-02):** `annex-slurm-finish` takes an exclusive `flock` on `<git-dir>/annex-slurm-finish.lock` for its whole run, including HEAD read, commit, push and rsync, so concurrent finishes on one repo queue instead of racing. The wait is `ANNEX_SLURM_LOCK_TIMEOUT` seconds (default 3600) and then fails loudly. Tests: a held lock blocks and times out, and two simultaneous finishes both land in history. So concurrent finishes are now safe. Concurrent `schedule` batches are still not designed or tested, and the lock relies on `flock` working on the repo's filesystem (NFS: kernel-dependent, not yet checked on `/cl_tmp`).

### Other limits

- Integration status: annex-slurm is in use for the 134 subregion flow (`.annex-slurm-managed` marker) and, since 2026-10-02, for **connectoflow's whole cohort path** (`connectoflow-slurm`, `scripts/submit_connectoflow_cohort.sh`). That one is the first end-to-end integration: setup registers one flat dataset per stage on the server's `derivatives` branch, the finish job runs `annex-slurm-finish` per stage and then verifies the server (ref equals HEAD, `git annex find --not --in origin` empty), exiting non-zero otherwise. It was tested with real git/annex/rsync against a local "server" and piloted for real on ds006707 (one subject; both stage refs and the annex content confirmed on `datalad-server`). `submit_bids_cohort.sh` (MRIQC/fMRIPrep/FreeSurfer) moved to annex-slurm on 2026-10-06: schedule via `annex_schedule_batch`, finish via `scripts/annex_cohort_finish.sh`, and the GUI's open-jobs panel/routes were removed (no DB to close). Validated end to end under a real scheduler by `annex-slurm/test/cohort_flow_e2e.sh`; **not yet run on a real production cohort** — pilot one subject (`submit --pilot`) first. The goal is a standalone repo.

## 6. Operational guardrails (HPC policy, in code)

- `execute_local()` raises `LoginNodeExecutionError` if `sbatch` is on PATH with no `SLURM_JOB_ID`. This covers the GUI Run button and the CLI `--local`. `--dry-run` is exempt.
- GUI daemon lifetime cap: it exits after 30 min idle on a login node. An hourly cron `login_node_hygiene.py` reaps abandoned processes (own UID only; vetoed if the process has children or a job id).
- `scripts/hooks/block_unscheduled_heavy_cmds.sh` is a PreToolUse hook that refuses compare and data-movement commands against `/cl_tmp` or `/datalad` unless they run under `srun`/`sbatch`/`salloc`.
- All bulk data is under `/cl_tmp/mrilabgraz`. Only `.sif` images and the FreeSurfer license live under `/usr/people`.
